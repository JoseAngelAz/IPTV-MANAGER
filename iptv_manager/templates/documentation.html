Stack Tecnológico

Backend

Python 3.11+ / 3.12
Lenguaje principal del backend.

¿Cómo funciona? Python es un lenguaje de programación interpretado, multiparadigma y tipado dinámico. Se ejecuta línea por línea a través del intérprete de Python, sin necesidad de compilación previa. Su amplio ecosistema de librerías (PyPI) permite agregar funcionalidades rápidamente. En este proyecto se usa con Django para manejar toda la lógica del servidor: autenticación, CRUD, reportes, etc.

Django 5.1.7
Framework web MTV con ORM.

¿Cómo funciona? Django sigue el patrón MTV (Model-Template-View). El Modelo define la estructura de datos en Python y Django lo traduce a tablas SQL automáticamente (ORM). La Vista contiene la lógica de negocio: recibe una petición HTTP, consulta la BD, y devuelve una respuesta. La Plantilla (Template) es HTML con sintaxis DTL que Django renderiza con los datos de la vista. Incluye autenticación, admin, CSRF, y más baterías incluidas.

Gunicorn 23.0.0
WSGI server para producción.

¿Cómo funciona? Gunicorn (Green Unicorn) es un servidor WSGI que recibe peticiones HTTP del proxy reverso (Nginx) y las pasa a la aplicación Django. Usa un modelo de workers pre-fork: crea N procesos hijo que compiten por las peticiones entrantes. Cada worker ejecuta Django de forma independiente. En este proyecto se configura con 2 workers como balance entre rendimiento y consumo de memoria.

WhiteNoise 6.8.2
Sirve archivos estáticos.

¿Cómo funciona? WhiteNoise intercepta las peticiones a archivos estáticos (CSS, JS, imágenes) directamente desde Python, sin necesidad de un servidor web separado como Nginx para esta tarea. Comprime los archivos con gzip, agrega cabeceras de caché (Cache-Control) y sirve versiones con hash para cache-busting. Esto simplifica el despliegue al eliminar la necesidad de configurar un servidor de estáticos separado.

django-htmx 1.19.0
AJAX sin JavaScript.

¿Cómo funciona? django-htmx integra HTMX con Django, permitiendo hacer peticiones AJAX sin escribir JavaScript. HTMX extiende HTML con atributos como hx-get, hx-post y hx-target. Cuando el usuario hace clic en un elemento con estos atributos, HTMX envía una petición asíncrona al servidor y reemplaza el contenido del target con la respuesta HTML. Django procesa la petición normalmente y devuelve HTML parcial.

django-axes 6.0.2
Protección fuerza bruta.

¿Cómo funciona? django-axes monitorea los intentos de inicio de sesión. Cuando detecta múltiples fallos (5 intentos por defecto) desde la misma IP y usuario, bloquea temporalmente el acceso durante 1 hora. Cada intento fallido se registra en la tabla axes_accessattempt. Cuando el usuario excede el límite, axes devuelve un HTTP 403 y muestra una página de "bloqueado". Esto evita ataques automatizados de diccionario.

python-decouple 3.8
Variables de entorno.

¿Cómo funciona? python-decouple lee configuraciones desde un archivo .env o desde variables de entorno del sistema. Separa la configuración del código, permitiendo tener diferentes ajustes en desarrollo, pruebas y producción. Usa config('VARIABLE', default=valor, cast=tipo) para obtener cada valor con tipado seguro. Los secretos como SECRET_KEY nunca se escriben en el código fuente.

Requests 2.32.3
Cliente HTTP.

¿Cómo funciona? Requests es una librería HTTP para Python que simplifica el envío de peticiones GET, POST, PUT, DELETE a APIs externas. Maneja automáticamente sesiones, cookies, cabeceras, timeouts y autenticación. En este proyecto se usa para enviar notificaciones vía WhatsApp/email a través de APIs de terceros, y para consultar servicios externos.

Pillow 12.2.0
Procesamiento imágenes.

¿Cómo funciona? Pillow (PIL Fork) es una librería de procesamiento de imágenes. Abre, manipula y guarda imágenes en múltiples formatos. En este proyecto, cuando un usuario sube una foto de perfil o un cliente, Pillow redimensiona la imagen a 400px de ancho (manteniendo aspect ratio) y la comprime al 70% de calidad JPEG para optimizar el almacenamiento. También genera thumbnails para vistas previas rápidas.

psycopg2-binary 2.9.10
Driver PostgreSQL.

¿Cómo funciona? psycopg2 es el adaptador de PostgreSQL para Python. Traduce las consultas del ORM de Django a comandos SQL que PostgreSQL entiende. Gestiona conexiones a la base de datos, pools, transacciones y tipos de datos específicos de PostgreSQL (arrays, JSONB, etc.). La versión -binary incluye las librerías compiladas para facilitar la instalación sin necesidad de compilar desde código fuente.

Frontend

Django Templates (DTL)
Sistema de plantillas nativo.

¿Cómo funciona? DTL (Django Template Language) es el motor de plantillas incluido en Django. Permite mezclar HTML con etiquetas {% templatetag openblock %} {% templatetag closeblock %} (bloques, bucles, condicionales) y variables {% templatetag openvariable %} {% templatetag closevariable %}. Las plantillas heredan de un layout base mediante {% templatetag openblock %} extends {% templatetag closeblock %}, redefiniendo bloques específicos. Django procesa la plantilla en el servidor, sustituye las variables con los datos del contexto, y devuelve HTML completo al navegador.

HTMX 1.9.12
AJAX dinámico sin recargas.

¿Cómo funciona? HTMX permite actualizar partes de la página sin recargarla completamente. Mediante atributos HTML como hx-get="url", hx-post="url" y hx-target="#id", cualquier elemento puede disparar una petición AJAX. El servidor responde con HTML (no JSON) que HTMX inserta en el elemento target. También soporta eventos, triggers (hx-trigger="cada 5s"), e intercambio de contenido con transiciones suaves.

Tailwind CSS 3.x
Framework CSS utility-first.

¿Cómo funciona? Tailwind CSS es un framework "utility-first": en lugar de escribir CSS personalizado, se aplican clases predefinidas directamente en el HTML (class="flex items-center p-4 bg-blue-500 text-white rounded"). Esto acelera el desarrollo y evita la proliferación de archivos CSS. Se carga via CDN con tailwind.config para personalizar colores y modo oscuro. Si el CDN falla, un CSS local de respaldo (fallback.css) toma el control.

Chart.js 4.4.7
Gráficos interactivos.

¿Cómo funciona? Chart.js crea gráficos vectoriales en un canvas HTML5. Recibe datos como arrays de JavaScript y configuración visual (colores, etiquetas, animaciones). Soporta múltiples tipos: barras, doughnut (anillo), línea, radar, etc. En el dashboard se usa para mostrar ingresos vs egresos (barras agrupadas), distribución de planes (doughnut), suscripciones en el tiempo (línea) y predicciones (barras). Los datos se pasan serializados en JSON desde el servidor.

Font Awesome 6.5.1
Iconos vectoriales.

¿Cómo funciona? Font Awesome proporciona una colección de iconos vectoriales (SVG) que se usan como fuentes o SVGs inline. Se carga via CDN y se inserta con etiquetas <i class="fas fa-home"></i>. Cada icono es escalable (se controla con font-size), coloreable con color, y animable con CSS. Se usa extensamente en navegación, botones, encabezados, tablas y documentación para mejorar la legibilidad visual.

Infraestructura

Docker 24+ / Compose v2
Contenedores multi-servicio.

¿Cómo funciona? Docker empaqueta la aplicación y sus dependencias en un "contenedor" aislado que se ejecuta de forma idéntica en cualquier sistema. El Dockerfile define cómo construir la imagen (instalar Python, copiar código, configurar Gunicorn). docker-compose.yml orquesta múltiples contenedores: web (Django+Gunicorn), db (PostgreSQL), nginx (proxy). Cada servicio se comunica a través de una red interna de Docker.

WhatsApp API (whatsapp-web.js)
API de mensajería WhatsApp.

¿Qué es? Es un microservicio Node.js en whatsapp-api/ que expone un endpoint HTTP POST /api/send para enviar mensajes de WhatsApp. Usa la librería whatsapp-web.js que automatiza WhatsApp Web a través de Puppeteer (Chromium headless). Se ejecuta en un contenedor Docker aparte (docker-compose: whatsapp) en el puerto 3000.

¿Cómo funciona? Al iniciar el contenedor, genera un código QR que debes escanear con WhatsApp en tu celular (solo la primera vez). La sesión se guarda en un volumen persistente whatsapp_session. Django envía peticiones POST a WHATSAPP_API_URL (configurable en .env) con el número y mensaje. El servicio recibe la petición, busca o crea el chat, y envía el mensaje. Soporta autenticación persistente, reconexión automática y cola de mensajes.

Configuración: La URL se define en WHATSAPP_API_URL=http://localhost:3000/api/send para desarrollo local, o http://whatsapp:3000/api/send dentro de la red de Docker. En producción detrás de Nginx, se puede exponer bajo /whatsapp/ con proxy reverso. Ver logs con docker-compose logs -f whatsapp.

Nginx 1.27
Reverse proxy, SSL, estáticos.

¿Cómo funciona? Nginx actúa como puerta de entrada al sistema. Recibe peticiones HTTP/HTTPS del exterior y decide cómo manejarlas: archivos estáticos (CSS, JS, imágenes) los sirve directamente desde el disco para máxima velocidad; las peticiones dinámicas (/) las reenvía (proxy reverso) a Gunicorn. También termina el cifrado SSL (Certbot), comprime respuestas con gzip, y agrega cabeceras de seguridad (HSTS, XSS).

PostgreSQL 16
Base de datos relacional.

¿Cómo funciona? PostgreSQL es un motor de base de datos relacional objeto-orientado. Almacena los datos en tablas con relaciones definidas por claves foráneas (FK). Soporta transacciones ACID, consultas complejas con JOIN, índices para búsquedas rápidas, y funciones avanzadas como JSONB, índices parciales y búsqueda de texto completo (FTS). Django se conecta mediante psycopg2 y el ORM genera automáticamente las consultas SQL.

PostgreSQL 16
BD relacional producción.

¿Cómo funciona? PostgreSQL es un motor de base de datos relacional objeto-orientado. Almacena datos en tablas con filas y columnas, garantizando integridad referencial mediante claves foráneas, restricciones CHECK y transacciones ACID. Soporta índices avanzados (B-tree, GiST, GIN), vistas, funciones almacenadas y JSONB. Django se conecta mediante psycopg2 y el ORM traduce objetos Python a consultas SQL optimizadas.

SQLite 3
BD ligera desarrollo local.

¿Cómo funciona? SQLite es una base de datos embebida que almacena toda la información en un solo archivo local. No requiere servidor, configuración ni credenciales. Es ideal para desarrollo porque es portátil (el archivo .db se puede copiar y compartir) y no necesita instalar PostgreSQL en la máquina local. Django cambia automáticamente entre SQLite y PostgreSQL según la variable de entorno USE_SQLITE.

Flujo de una petición

  1. Browser → HTTPS → Nginx (puerto 443)
  2. Nginx sirve /static/ directamente (o WhiteNoise)
  3. Nginx pasa / a Gunicorn (proxy_pass)
  4. Gunicorn ejecuta Django → WSGI → middleware chain
  5. Axes verifica intentos de login (fuerza bruta)
  6. URL dispatcher → View con permisos RBAC
  7. View consulta ORM → PostgreSQL
  8. Template renderiza HTML + HTMX + Chart.js
  9. Respuesta viaja de vuelta al browser

Seguridad

Cada medida de seguridad implementada incluye una explicación de qué protege y cómo funciona. Haz clic en cada una para expandir.

Secret Key Implementación: python-decouple, sin default en código

¿Qué es? La SECRET_KEY es una cadena aleatoria que Django usa para firmar cookies, tokens CSRF, contraseñas (hash), y datos de sesión. Es la base criptográfica de toda la seguridad de Django.

¿Cómo funciona? La clave se almacena en el archivo .env mediante python-decouple y nunca se escribe en el código fuente. Se genera con secrets.token_urlsafe(50). Si un atacante obtuviera esta clave, podría falsificar cookies, tokens CSRF y contraseñas. Por eso se mantiene fuera del repositorio Git.

DEBUG mode Implementación: False por defecto vía env var

¿Qué es? El modo DEBUG de Django muestra trazas de error detalladas (tracebacks completos, variables, configuración) cuando ocurre una excepción. Útil en desarrollo pero peligroso en producción.

¿Cómo funciona? Cuando DEBUG=True y ocurre un error, Django muestra una página con información sensible: valores de variables, rutas del sistema, configuraciones, credenciales de BD. Un atacante podría explotar esta información para encontrar vulnerabilidades. En este proyecto, DEBUG se controla con la variable de entorno y por defecto es False en producción.

Fuerza Bruta (django-axes) Implementación: 5 intentos, 1h cooloff, bloqueo IP+usuario

¿Qué es? Un ataque de fuerza bruta intenta adivinar contraseñas probando miles de combinaciones automáticamente. django-axes los detecta y bloquea temporalmente.

¿Cómo funciona? Cada intento fallido se registra con IP, usuario y timestamp en la tabla axes_accessattempt. Cuando se superan 5 fallos para la misma IP+usuario, axes devuelve HTTP 403 y muestra una página "bloqueado" por 1 hora. El cooloff es acumulativo: más intentos = más tiempo de bloqueo. Esto hace que los ataques automatizados sean imprácticos.

HSTS (HTTP Strict Transport Security) Implementación: 31536000s (1 año), includeSubDomains, preload

¿Qué es? HSTS es una cabecera HTTP que obliga al navegador a conectarse siempre mediante HTTPS, eliminando la posibilidad de conexiones HTTP inseguras.

¿Cómo funciona? Cuando el navegador recibe la cabecera Strict-Transport-Security: max-age=31536000; includeSubDomains; preload, la almacena para ese dominio por 1 año. Durante ese periodo, el navegador rechazará cualquier conexión HTTP y usará HTTPS automáticamente, incluso si el usuario escribe http:// o hace clic en un enlace HTTP. Esto previene ataques "Man-in-the-Middle" como SSL stripping.

XSS (Cross-Site Scripting) Implementación: SECURE_BROWSER_XSS_FILTER = True

¿Qué es? XSS permite a un atacante inyectar código JavaScript malicioso en páginas web vistas por otros usuarios. Puede robar cookies, tokens, o redirigir a sitios falsos.

¿Cómo funciona? Django auto-escapa todas las variables en las templates: caracteres como <, >, &, " se convierten a sus entidades HTML, evitando que se interpreten como código. Además, la cabecera X-XSS-Protection activa el filtro anti-XSS del navegador. No se usa mark_safe() ni HTML sin escapar. El 100% de las consultas usan ORM (nunca SQL raw), eliminando también la inyección SQL.

Content Sniffing (MIME sniffing) Implementación: SECURE_CONTENT_TYPE_NOSNIFF = True

¿Qué es? El MIME sniffing es una característica de navegadores antiguos que "adivina" el tipo de contenido de un archivo basándose en su contenido, ignorando el Content-Type declarado por el servidor. Un atacante puede subir un archivo .jpg con JS malicioso que el navegador ejecutará como HTML.

¿Cómo funciona? La cabecera X-Content-Type-Options: nosniff le indica al navegador que confíe estrictamente en el Content-Type declarado y no intente adivinar el tipo de archivo. Así, un archivo servido como image/jpeg siempre se tratará como imagen, incluso si contiene código HTML/JS. Esto previene ataques de "polyglot" (archivos válidos en múltiples formatos).

Clickjacking (Frame Options) Implementación: X_FRAME_OPTIONS = 'DENY'

¿Qué es? Clickjacking engaña al usuario para que haga clic en elementos invisibles de un sitio web legítimo mientras cree que está interactuando con otro sitio. Por ejemplo, un botón falso en un sitio malicioso que cubre el botón "Eliminar cuenta" del sitio real.

¿Cómo funciona? La cabecera X-Frame-Options: DENY impide que el sitio se cargue dentro de un <iframe>, <frame> o <object> en otro dominio. Si un atacante intenta incrustar el sistema en un iframe, el navegador lo rechazará y mostrará un espacio vacío. Esto hace imposible el ataque de "hijacking de clics".

Cookies Seguras (Secure + HttpOnly) Implementación: SESSION_COOKIE_SECURE + CSRF_COOKIE_SECURE condicional a HTTPS

¿Qué es? Las cookies de sesión y CSRF contienen tokens de autenticación. Si un atacante las intercepta, puede suplantar al usuario (session hijacking).

¿Cómo funciona? La bandera Secure hace que el navegador solo envíe la cookie a través de conexiones HTTPS cifradas, nunca por HTTP plano. La bandera HttpOnly (activada por defecto) impide que JavaScript acceda a la cookie usando document.cookie, protegiendo contra ataques XSS que intenten robar la sesión. En este proyecto, estas banderas se activan condicionalmente cuando HTTPS=True en el entorno.

Validación de Input (teléfono, MAC) Implementación: RegexValidator para E.164 y XX:XX:XX:XX:XX:XX

¿Qué es? La validación de entrada asegura que los datos ingresados por el usuario tienen el formato esperado antes de procesarlos o almacenarlos, evitando inyecciones y datos corruptos.

¿Cómo funciona? Django usa RegexValidator con patrones de expresión regular para verificar que el teléfono cumple con el formato E.164 (+521234567890) y que el ID de dispositivo (MAC) tiene el formato XX:XX:XX:XX:XX:XX. Si el usuario ingresa un formato inválido, el formulario muestra un error y no guarda los datos. Esto previene inyección de datos maliciosos y mantiene la integridad de la base de datos.

RBAC (Control de Acceso por Roles) Implementación: @login_required + PermissionRequiredMixin en TODAS las vistas

¿Qué es? RBAC (Role-Based Access Control) restringe el acceso a funcionalidades según el rol del usuario. No todos los usuarios pueden hacer todo: solo los administradores pueden eliminar, solo soporte puede ver clientes, etc.

¿Cómo funciona? El sistema de permisos de Django asigna permisos específicos (view_cliente, delete_cliente, view_movimientofinanciero) a grupos (Admin, Soporte, Consulta). Las vistas verifican estos permisos con @login_required (usuario autenticado), @permission_required (permiso específico), o PermissionRequiredMixin (CBV). También hay verificaciones adicionales con request.user.is_superuser para acciones críticas como eliminar logs.

Protección SQLi / XSS en BD Implementación: 100% ORM + auto-escape templates, sin mark_safe

¿Qué es? SQL Injection ocurre cuando un atacante inserta código SQL malicioso en campos de entrada, engañando a la base de datos para que ejecute comandos no autorizados (leer, modificar o borrar datos).

¿Cómo funciona la protección? Django ORM (Object-Relational Mapper) nunca concatena SQL directamente. En lugar de escribir SELECT * FROM cliente WHERE nombre = '"+input+"', se usa Cliente.objects.filter(nombre=input). El ORM parametriza automáticamente las consultas, escapando los valores de entrada. Incluso si el usuario escribe '; DROP TABLE cliente; --, Django lo trata como un valor literal de búsqueda, no como SQL ejecutable.

CSRF (Cross-Site Request Forgery) Implementación: CsrfViewMiddleware + {% templatetag openblock %} csrf_token {% templatetag closeblock %} en todos los formularios

¿Qué es? CSRF engaña al navegador de un usuario autenticado para que envíe una petición maliciosa (cambio de contraseña, transferencia, etc.) a un sitio donde el usuario tiene sesión activa.

¿Cómo funciona? Cada formulario incluye un token CSRF único generado por Django: {% templatetag openblock %} csrf_token {% templatetag closeblock %}. Este token está vinculado a la sesión del usuario y expira después de un tiempo. Cuando el formulario se envía, Django verifica que el token coincida con el de la sesión. Un sitio malicioso no puede obtener este token (protegido por Same-Origin Policy), por lo que cualquier petición POST sin token válido es rechazada con error 403.
